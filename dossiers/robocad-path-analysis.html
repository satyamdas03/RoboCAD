Which revolution should RoboCAD build next?

A research-grounded comparison of PATH1 (GEDA Bridge / Phase 15) and PATH2 (voice-to-CAD-to-simulation-to-world-model).

Recommended first path
PATH1: GEDA Bridge
Why now
It extends what already works and feeds a $4–5 B market that is desperate for CAD-to-simulation glue.
PATH2 status
The right North Star, but too many unsolved sub-problems to chase before PATH1 is shipped.
Immediate next step
Get Claude Sonnet 5 benchmark to ~80%, then build the MuJoCo exporter as Phase 14/15.

Executive summary

You have two visions on the table. They are not alternatives; they are sequential layers of the same company. The question is order, not either/or.

  • PATH1 (GEDA Bridge) is a delivery infrastructure play: take the parametric CAD parts RoboCAD already produces and export them cleanly into MuJoCo/URDF with correct inertial properties, DFM reports, and a bundle schema that LearningRobotics can consume. It is technically reachable from the current codebase, has a narrow, well-defined scope, and sits at the intersection of several fast-growing markets: robot skill-learning platforms (~$4–5 B in 2026), physical AI simulation (~$3.8 B+), and synthetic-data generation for robotics (~$2.5 B).
  • PATH2 (voice/text → CAD → physical test → assembly → world model → HERMES supervisor) is a full-stack robotics design operating system. It is ambitious, defensible, and aligns with where the industry is heading (NVIDIA Cosmos, foundation models for physical AI, sim-to-real). But it bundles too many unsolved or half-solved sub-problems — reliable voice parsing for engineering intent, part-level physical simulation of arbitrary CAD, automated assembly synthesis, and a generalist supervisory agent — into one bet.

The recommendation: ship PATH1 first. It validates the CAD-to-physics handoff, produces a reusable asset format, and creates the exact data and API surface that PATH2 will need later. PATH2 becomes the natural second act once PATH1 is proven with a real LearningRobotics handshake.

Delivery infrastructure for RoboCompiler

Interpretation: The “revolutionary” part is not the bridge itself; it is the workflow the bridge enables. RoboCompiler (human video → skill) is the high-value surface, but it cannot exist without clean, physically-grounded assets. GEDA Bridge is the picks and shovels for that revolution. That is a strong place to be: lower risk than the end-to-end consumer product, but directly tied to its growth.

1.2 Technical feasibility from the current state

RoboCAD today has:

  • Parametric code generation (build123d) with self-correction.
  • Feature-tree schema v1, transpiler, and backend endpoints.
  • Assembly system with LCS-based mates.
  • DFM rule engine, tolerance/fit checks, simple FEA.
  • STL/STEP export and design persistence.

What GEDA Bridge needs on top:

  • Convert build123d Shape → metric mesh (already STL).
  • Compute mass properties from a real density (build123d/trimesh can give volume; multiply by density).
  • Write MJCF with <inertial> tag and convex collision mesh.
  • Write URDF as a compatibility layer.
  • Package directory structure per the v2 bundle schema.

None of these are research problems. They are plumbing and unit-conversion problems. The hardest piece is getting the inertia tensor correct in the right coordinate frame and units — that is well-documented in MuJoCo and URDF specs. The Phase 15 prompt’s verification thresholds (mass > 0, positive-definite inertia, CoM inside bounding box) are sanity checks, not moonshots.

1.3 Competitive landscape

The GEDA Bridge sits between CAD and simulators. Existing players:

  • NVIDIA Isaac Sim / Isaac Lab: Photoreal, GPU-parallel, synthetic data leader. Requires NVIDIA stack, steep setup. RoboCAD’s angle is “small, deterministic, open-source, LLM-generated parametric parts” — a different shape.
  • MuJoCo ecosystem: Gold standard for contact-rich RL. No turnkey CAD importer. GEDA Bridge fills exactly that gap.
  • Gazebo Harmonic / ROS 2: Systems integration default. URDF export from RoboCAD makes you compatible here.
  • Siemens / Dassault / PTC / Autodesk: PLM/CAD giants with digital twins. They are not focused on LLM-generated hobbyist/startup robotics parts. Their tools are expensive and heavy; RoboCAD is lightweight and code-first.
  • Skild AI, Physical Intelligence, Generalist, HOST, Video2Robo: The video-to-skill competitors. They do not design custom parts; they assume the robot morphology is fixed. RoboCompiler + GEDA Bridge’s unique angle is: if the task needs a custom gripper/wedge/bracket, design it in RoboCAD, verify it, then learn the skill.

1.5 Verdict on PATH1

Do this first. It is technically reachable, market-validated, and creates the exact artifact (bundle schema + verified MJCF) that PATH2 needs. It also gives RoboCAD a concrete integration story beyond “we generate STL files.”

2. PATH2: Voice/text → CAD → physical simulation → assembly → world model

The full-stack robotics design OS

2.1 Parsing the vision

PATH2 is actually a stack of five distinct products:

  1. Voice/text intent parser for engineering designs. Convert natural speech into structured design parameters. This is closer to a voice-driven CAD copilot than a generic assistant.
  2. Automated part decomposition. For complex designs (humanoid), break the intent into individual parts with interfaces and mates. This is an AI planning problem on top of CAD.
  3. Part-level physical simulation. Test each part under load, fatigue, wear before assembly. This is FEA/physics simulation, not just geometry validation.
  4. Automated assembly synthesis. Combine parts into a final assembly and verify end-to-end behavior. This is the GEDA Bridge plus higher-level planning.
  5. World-model simulation + robot brain training. Put the assembled robot into a simulated world, train a policy on synthetic data, evaluate, retrain. This is LearningRobotics / RoboCompiler territory.
  6. HERMES supervisor. A conversational agent that watches the whole pipeline, explains status, and accepts commands. This is a meta-orchestration layer.

Each of these is a serious project. Bundling them into one phase is dangerous because progress is gated by the weakest link.

2.2 Market context

The markets PATH2 touches are large and real, but they are mostly downstream of GEDA Bridge:

  • Generative AI in product design & engineering: ~$7 B in 2026, growing 24% CAGR. Voice-to-CAD is a tiny slice, but the broader “AI-assisted mechanical design” tailwind is strong.
  • Digital twin / manufacturing simulation: ~$35–47 B in 2026. Part of this is exactly “test before build,” but incumbents (Siemens, Ansys, Dassault) own the high end.
  • Physical AI training platforms: ~$3.2 B base, forecast to $101 B by 2035 at 41% CAGR. This is the world-model + synthetic-data layer.
  • Conversational robotics supervision: Emerging academic area (JARVIS projects, MCP/ACP protocols). No clear standalone market yet, but it is a UX differentiator.

Interpretation: PATH2’s market opportunity is the union of several multi-billion-dollar markets, but the path is crowded and capital-intensive. The incumbents’ moat is integration: they sell CAD + CAE + PLM + simulation as one stack. A startup wins by owning a narrow, hard wedge first.

2.4 Competitive landscape

  • MIT “Speech to Reality” (2025): Voice → LLM → text-to-3D → voxelized components → robot assembly. It closes the loop, but the output is voxel/modular, not parametric CAD. RoboCAD’s differentiation is parametric, editable, manufacturable parts.
  • SolidVoice / VoiceForge: Voice-to-CAD for SolidWorks/FreeCAD. They are plugins; RoboCAD is a native AI-first stack.
  • NVIDIA Cosmos + GR00T: World foundation models and humanoid training. They will not design custom hardware for you; they assume a fixed robot. RoboCAD’s angle is “design the robot, then train it.”
  • Siemens Industrial Copilot / Rockwell / Schneider: Natural-language industrial automation. They are not doing generative mechanical design for small robotics teams.

2.5 Risks

Risk Severity Mitigation
Scope explodes across 6 products High Sequence into independent phases; ship each layer before adding the next.
Voice is a gimmick for engineering intent Medium Treat voice as an input modality, not the core UX. Text remains primary.
Physical simulation for arbitrary parts is brittle High Start with load-case templates (drop test, static load), not open-ended FEA.
Training a robot brain is a full-stack ML project High Leave policy training to LearningRobotics; RoboCAD only provides the asset.
HERMES becomes a black-box bottleneck Medium Build it as a supervisor/observer first, not the sole executor.

2.6 Verdict on PATH2

The right North Star, but the wrong next milestone. PATH2 describes the company you want to be in 3–5 years. It should guide architecture (why the bundle schema matters, why MJCF must be correct, why HERMES should observe the pipeline), but it should not be the immediate build target. Chasing it now spreads effort too thin and substitutes a vision for a shipped product.

4. Recommended sequencing

4.1 Phase A — Complete the current RoboCAD core (now)

  • Finish Claude Sonnet 5 benchmark tuning. Target: ≥80% on T1–T4 before moving on. The 70% run shows T1–T3 are mostly solved; T4/T5 need either better prompting, feature-tree path, or constrained code templates.
  • Keep local model training as a background optimization, not the main blocker.
  • Commit and push after each fix.

4.2 Phase B — Build the MuJoCo exporter (Phase 14/15A)

This is PATH1 in practice:

  1. Exporter module: ai_cad/geda_bridge/exporter.py with export_to_mujoco() matching the signature in the Phase 15 prompt.
  2. Outputs: part.stl, part_collision.stl, part.mjcf, part.urdf, inertial.json, manifest.json.
  3. Tests: cube, cylinder, L-bracket, 2-part assembly. Verify mass, CoM, inertia, and MuJoCo load.
  4. API: POST /designs/{id}/simulate, GET /designs/{id}/simulation, GET /designs/{id}/bundle.
  5. Example bundles: gripper_cube_grasp, bracket_hook_hang, wedge_push_block.

4.3 Phase C — Cross-repo handshake with LearningRobotics

  • LearningRobotics loads the bundle and runs a stability rollout.
  • Compose the part into a standard manipulation scene.
  • Verify one simple skill (push block with wedge).
  • Register the verified pair via /capabilities.

4.4 Phase D — Voice and decomposition (PATH2 begins)

Only after PATH1 is proven:

  • Add Whisper STT as an input modality; keep text primary.
  • Build a design-decomposition planner that breaks complex prompts into a feature tree + assembly plan.
  • Add load-case templates for part-level physical testing.
  • Introduce HERMES as a conversational observer/status reporter, not the sole controller.

4.5 Phase E — World model and brain training

This is mostly LearningRobotics’ domain. RoboCAD’s role is to keep producing better, simulation-ready assets and to accept feedback from the world-model results.

5. What to build this week

  1. Re-run the 30-prompt benchmark with the latest extractor fix and topped-up Claude credits. Confirm the 70% result holds or improves.
  2. Debug remaining T4/T5 failures. Likely causes: max_tokens still too low for very long outputs, or the system prompt does not instruct Claude to keep code blocks clean during self-correction. Try adding an explicit instruction: “Always return corrected code in a single fenced python block with no nested fences.”
  3. Sketch the GEDA Bridge exporter API in a new branch or doc: ai_cad/geda_bridge/exporter.py interface, bundle schema v2, and test plan.
  4. Update PLAN.md to reflect: Phase 13 finishes at ~80% benchmark, Phase 14 expands to include the MuJoCo exporter + bundle packaging, Phase 15 is the LearningRobotics handshake.

6. Final recommendation

Build PATH1 first. It is the only path that converts today’s working RoboCAD into a product that another project (LearningRobotics) can actually consume. It validates the central thesis — that AI-generated parametric CAD can be physically useful — without requiring six separate miracles.

PATH2 is the destination. Let it shape the architecture, but do not try to build it whole. The sequence is: generate → validate → export → simulate → compose → learn. You are currently at “generate/validate.” PATH1 gets you to “simulate/compose.” That is exactly the right next step.
